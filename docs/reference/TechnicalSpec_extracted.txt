0. Purpose, Scope, and Ground Rules
0.1 What we are building
A Unity DOTS/ECS implementation of the Continuum Crowds algorithm (Treuille,
Cooper, Popović — SIGGRAPH 2006), faithfully reproducing the algorithmic core of thereference C# implementation yohash/ContinuumCrowds (Jason Heebl, MIT license),restructured for Burst-compiled, job-parallel execution.
Continuum Crowds (CC) replaces per-agent pathﬁnding with per-group dynamicpotential ﬁelds. Each update: unit density and velocity are stamped onto a grid; for each
group, a directional speed ﬁeld and cost ﬁeld are derived; the eikonal equation ‖ ∇ φ‖ = Cis solved outward from the group's goal; units move opposite the potential gradient,scaled by the local speed ﬁeld. Global navigation and local avoidance emerge from a
single optimization — no separate collision-avoidance regime, no local minima.
0.2 Performance targets
Baseline load: ~10,000 units, ~5 concurrent groups/solves, 512×512 world grid (1m cells nominal).
Solve cadence: velocity ﬁelds refresh at a controlled low rate (default 10 Hz),
decoupled from frame rate. (The original paper ran simulation updates at 2–5 fpsagainst a 24 fps renderer — low-rate solving is canonical, not a compromise.)
Frame budget: no single frame should carry more than one group's solve work; per-frame passes (stamping when scheduled, advection, min-distance) must ﬁtcomfortably in worker-thread time with zero main-thread stalls.
Everything Burst. All hot-path code is [BurstCompile]d. All systems are ISystem
(unmanaged). No managed allocations on any per-frame or per-solve path. No GC

"Into-cell" evaluation rule (critical, easy to get wrong): when computing the speed orcost for cell M in direction d, all density/velocity/discomfort/slope reads are taken
from the neighbor cell the mover would enter — M + ENSWint[d] — not from M itself.This is the discrete analog of the paper's r·n_θ offset and exists so a unit's own
density contribution never obstructs its own motion. The repo implements this as
xGlobalInto/yGlobalInto; reproduce it faithfully.

2.3 Density and average velocity (paper Eq. 7; repo computeUnitFields +
computeAverageVelocityField)
Accumulate over all units i (all groups — density is global and couples the groups):
ρ[c]    = Σ ᵢ   w_i(c) · mass ᵢv̄acc[c] = Σ ᵢ   w_i(c) · mass ᵢ  · velocity ᵢ         // momentum accumulation
--- PAGE 6 ---
v̄[c]    = ρ[c] > 0 ? v̄ acc[c] / ρ[c] : 0          // finalize: average velocity
where w_i(c) is unit i's footprint weight at cell c (§6.4).
⚠  DIVERGENCE (repo extension, kept): the paper has no mass term; the reposcales density by IContinuumUnit.Mass. We keep mass — it enables heterogeneous
units (vehicles, large creatures) for free.
Footprint requirement (paper §4.1, quoted in the repo's IContinuumUnit docs): eachunit must contribute no less than ρ̄ to its own cell and no more than ρ̄ to any
neighboring cell. Combined with f_rhoMin ≥ ρ̄, this guarantees an isolated unitalways moves at topographical speed — it can never congest itself. Our footprint
construction (§6.4) must satisfy this invariant; add an editor-mode assertion test for it.
2.4 Speed ﬁeld f (paper Eqs. 8–10; repo computeSpeedFieldPoint)
For cell M, direction d, with into = M + ENSWint[d]:
1. If into is invalid (out of bounds, or g[into] ≥ 1 = impassable): f =
f_speedMin.
2. Read ρ_into = ρ[into].
3. Low density (ρ_into < f_rhoMin) →  topographical speed:
slope = dot( ∇ h[into], ENSW[d])
f_T   = f_speedMax + (slope − f_slopeMin) / (f_slopeMax − f_slopeMin) · (f_speedMin − f_speedMax)f     = f_T
(Downhill in the direction of travel →  faster; uphill →  slower.)
4. High density (ρ_into > f_rhoMax) →  ﬂow speed:
f_v = max(0, dot( v̄ [into], ENSW[d]))f   = f_v
The max(0, ·) clamp is mandatory (repo changelog v0.2.7, quoting the paper): the
crowd can slow you down but never carry you backwards. This clamp + directionaldot product is the term that produces lane formation — do not "optimize" it away.
5. Medium density →  linear interpolation:
f = f_T + (ρ_into − f_rhoMin) / (f_rhoMax − f_rhoMin) · (f_v − f_T)
6. Final clamp: f = clamp(f, f_speedMin, f_speedMax).
2.5 Unit cost ﬁeld C (paper Eq. 4; repo computeCostFieldValue)
--- PAGE 7 ---
For cell M, direction d, with into = M + ENSWint[d]:
1. If f[M][d] == 0orinto invalid →  C = +∞ (float.PositiveInfinity). (Zero
speed would divide by zero; invalid cells are unreachable.)
2. Read discomfort of the into-cell and clamp: g' = clamp(g[into], 0, 1).
⚠  DIVERGENCE (repo, kept): the paper leaves g unbounded; the repo clamps to[0,1] and treats g ≥ 1 as absolutely impassable, folding boundaries into thediscomfort ﬁeld. We keep this — it's cleaner than a separate boundary mask.
3. C = C_alpha + C_beta · (1 / f) + C_gamma · (g' / f)
Algebraically identical to the paper's C = (αf + β + γg)/f.
2.6 Eikonal equation and potential φ (paper Eq. 5 & 11; repo EikonalSolver)
φ = 0 on the goal; elsewhere ‖ ∇ φ(x)‖ = C evaluated in the gradient direction. Optimalpaths follow − ∇ φ. Solved per group, per solve tick, over that group's domain (§8), by
FMM or FIM (§9–10). The ﬁnite-difference update formula shared by both solvers isspeciﬁed in §9.3–9.4.
2.7 Velocity derivation (paper Eq. 6; repo gradient +
calculateVelocityField)
v(x) = −f(x, θ_motion) · ∇ φ(x) / ‖∇ φ(x) ‖
Gradient computed per §11 (central difference + inﬁnity fallback, normalized), theneach component is scaled by the direction-appropriate face of the anisotropic speed
ﬁeld:
velocity.x = dPhi.x > 0 ? -f[i][2] * dPhi.x   // moving −x: use W face                        : -f[i][0] * dPhi.x;  // moving +x: use E facevelocity.y = dPhi.y > 0 ? -f[i][3] * dPhi.y   // moving −y: use S face

2.9 Emergent phenomena — the acceptance criteria
The implementation is correct only if it reproduces, without any special-case code:
Lane formation: two groups walking in opposite directions through a corridor
segregate into lanes. Driven by the ﬂow-speed term (§2.4 step 4).
Vortex formation: four groups crossing to opposite corners form a rotating pattern.
Smooth congestion avoidance: units reroute around forming congestion before
reaching it; near-zero collisions and no sudden heading changes in moderatedensity.
No local-minima trapping: units never get stuck behind obstacles or crowds(guaranteed by global φ optimality).
These are the Phase-1/2 validation scenarios (§15).
3. ECS Data Architecture
3.1 Design principle (Decision D1)
Grid cells are not entities. Every ﬁeld operation is neighbor-relative; with cells-as-
entities, neighbor reads become cross-chunk entity lookups that destroy cachecoherence. Cells have no lifecycle and no identity. Therefore:
Entities = things with identity/lifecycle: units, groups (solve requests), plus ahandful of singletons.
Flat native containers = all bulk ﬁeld data, owned by singleton components holding
the containers, allocated Allocator.Persistent at world init.
Jobs bridge the two: IJobEntity reads/writes unit components;
IJobParallelFor/IJob operate on ﬁeld arrays.

6. Pass 1 — Stamping (gather pattern)
6.1 Why gather (Decision D3, recorded rationale)
Three candidate parallelization patterns were evaluated:
Scatter with atomics: each unit atomically adds into ρ/v̄acc. Rejected: atomic ﬂoatadds serialize under contention exactly where crowds are densest — worstperformance precisely where correctness matters most.
Scatter with per-thread buffers + reduction: race-free, simple, but memory =threadCount × gridSize (e.g. 16 threads × 3 MB = 48 MB of scratch and a full-grid
reduction pass). Acceptable fallback; not default.
Gather (chosen): build a spatial hash of units; run a parallel job over cells, each cellpulling contributions from nearby units. Every cell written by exactly one thread —
--- PAGE 14 ---
no races, no atomics, no reduction, fully Burst-vectorizable. Cost scales withactiveCells × localUnitCount, and active cells are limited to hashed buckets
containing units.
6.2 Job structure
Job A (IJobEntity, parallel):  clear+rebuild UnitSpatialHash from unit entities                               (snapshot Position/Velocity/Mass/FootprintSize into UnitStampData)
Job B (IJobParallelFor over active cells): for each cell c:                               query hash buckets overlapping c's gather radius;                               ρ[c] = Σ w_i(c)·m_i;  v̄ acc[c] = Σ w_i(c)·m_i·v_iJob C (IJobParallelFor):       finalize v̄ [c] = ρ[c]>0 ? v̄ acc[c]/ρ[c] : 0
Jobs B and C can be fused; keep them separate initially for clarity/proﬁling, fuse inPhase-4 optimization if the extra grid pass shows up.
Active cell determination: collect the set of occupied buckets during Job A (a
NativeParallelHashSet<int> of bucket keys via parallel writer, or reuse the multi-hash-map's unique keys). Active cells = union of cells covered by occupied buckets
dilated by the gather radius. Cells outside the active set are cleared to zero with acheap parallel memclear restricted to previously active cells (track last tick's active set;clearing the whole 512² grid is also only ~3 MB of writes and acceptable if simpler —
measure, prefer simple ﬁrst).
6.3 Bucket sizing and gather radius
Let R_max = maximum footprint half-extent including predictive extension: R_max =
maxFootprintSize + u_unitRadialFalloff + v_predictiveSeconds · f_speedMax /
CellSize (in cells). Choose BucketSize = ceil(R_max) cells so that any cell'scontributors lie within its own bucket and the 8 neighbors — a ﬁxed 9-bucket query,branch-predictable and unrollable. If v_predictiveSeconds · f_speedMax makes
R_max large, cap the predictive extent (clamp extrapolation distance) rather thangrowing buckets unboundedly; document the cap next to the constants.
6.4 Footprint function w_i(c) — the density kernel
The repo delegates the footprint to the consumer (IContinuumUnit.Footprint, a
float[,] stamp) while documenting the paper's invariant. We must deﬁne a concrete
kernel. Requirements:
1. Continuity in unit position (else speed ﬁelds pop as units cross cell centers).
2. ρ̄ invariant: contribution ≥ ρ̄ to the unit's own cell, ≤ ρ̄ to any neighbor (paper §4.1),with f_rhoMin ≥ ρ̄ enforced by a conﬁg-time assert.
--- PAGE 15 ---
Chosen kernel — the paper's §4.1 splat, generalized: for the base (static) footprint, usethe paper's own construction. Let (Δx, Δy) be the unit's fractional position relative to
the nearest lower-left cell center; deposit onto the 2×2 neighborhood {A=lower-left,B=lower-right, C=upper-right, D=upper-left}:

7. Predictive Velocity (Decision D4)
7.1 Rationale (record verbatim in code docs)
--- PAGE 16 ---
The paper's §3.3 "predictive discomfort" deposits discomfort ahead of each movingunit so others avoid the space it is about to occupy. Rejected: a unit with projected
discomfort in front of itself will path-adjust to avoid its own projection; the projectionthen moves with the new heading, and the unit adjusts again — a feedback oscillation.
Predictive velocity (the repo's approach) instead extrapolates the unit's density/velocityfootprint forward along its velocity. Because the speed ﬁeld's ﬂow term (§2.4 step 4) isdirectional — moving with the local average velocity is not penalized — a unit is never
obstructed by its own forward projection when continuing straight, so no self-avoidanceloop exists. Additionally, forward-projected velocity strengthens v̄ along movement
corridors, which reinforces fast lanes and slow lanes: followers see high same-directionﬂow speed (cheap), opposers see it as resistance (expensive).
7.2 Speciﬁcation (repo semantics)
Constants: v_dynamicFootprintThreshold (default 0.25), v_predictiveSeconds
(1.0), v_scaleMax (0.3), v_scaleMin (0.25).
For a unit with speed s = length(velocity):
If s < v_dynamicFootprintThreshold: static footprint only (§6.4). No prediction.
Else: in addition to the static footprint at the current position, deposit a chain of
ghost stamps along the extrapolated path:
P_k = Position + Velocity · t_k,   t_k ∈  (0, v_predictiveSeconds], K ghost steps
scale(t_k) = lerp(v_scaleMax, v_scaleMin, t_k / v_predictiveSeconds)   // fades with lookaheadghost contribution at cell c:  scale(t_k) · SplatWeight(P_k, c, λ) · Mass  →  into ρ and ρ·v
Choose K so consecutive ghosts are ≤ 1 cell apart (K = ceil(s ·
v_predictiveSeconds / CellSize), clamped to a max, e.g. 8) — gaps in the ghostchain create striped density that ﬂickers the speed ﬁeld.
Gather-side implementation:PredictiveWeight(u, cc) inverts this — instead of theunit depositing K ghosts (scatter thinking), the cell checks its distance to the unit'sextrapolation segment[Position, Position + Velocity · v_predictiveSeconds]
and integrates the ghost weights that would land on it. A closed-form approximation isﬁne: project cc onto the segment, parameter t*, if the perpendicular distance is withinkernel support, contribute scale(t*) · SplatWeight(P(t*), cc, λ) (optionally × a
short tangential extent factor). This keeps the inner loop branch-light. Validate thegather-side formulation against a brute-force scatter reference in tests (§15).
Important stamping detail: ghost contributions add to both ρ and the momentumaccumulator (with the unit's full velocity), exactly like the real stamp — that is whatprojects the ﬂow ﬁeld forward, and it is the lane-formation booster. The into-cell speed

evaluation (§2.1) already prevents self-obstruction for the static stamp; the directionalﬂow clamp prevents it for the predictive stamp.

9. Eikonal Solver I — Fast Marching Method (FMM)
9.1 Role
The default solver for small/medium domains. One Burst IJob per group solve;parallelism comes from solves running concurrently across groups on separate workerthreads. FMM is inherently serial (a single global priority queue) but does minimal total
work — each cell is ﬁnalized exactly once, O(N log N).

10. Eikonal Solver II — Fast Iterative Method (FIM) + hybrid
decider
10.1 Why FIM (Decision D8)
FMM's priority queue makes one solve one thread. Fine for 5 medium domains (5
concurrent jobs). But a single huge domain (the paper's army scenarios; a full-mapgroup) bottlenecks on one core while others idle. FIM (Jeong & Whitaker, 2008)removes the global queue: cells sit on an active list and are iteratively relaxed with the
--- PAGE 22 ---
same update formula (§9.3–9.4) until convergence; active cells within an iteration areorder-independent and can be updated in parallel. FIM does modestly more total work
than FMM (cells can be updated multiple times before converging; overhead grows withcost-ﬁeld heterogeneity), but the inner loop is branch-light, has no queue, and vectorizes
— very Burst-friendly — and it scales across all workers.
10.2 Algorithm (per-cell FIM, CPU-adapted)

FIM and FMM must agree on φ to within eps on identical (domain, C) inputs — this is astanding automated test (§15). The weighted-root formula (§9.4) is not the classicaleikonal update, but it is a consistent monotone-ish local solver shared by both;

deterministic given the hash snapshot).
Single iteration per frame (repo/paper: not strictly convergent, occasionally pushesstationary units — accepted artifact, converges across frames).
Known paper caveat to preserve in comments: enforcement can push non-movingunits; the vast majority of the time it cleanly removes intersections the grid can'tresolve.
